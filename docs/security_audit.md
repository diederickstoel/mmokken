## 🔴 Blocker: respondent-level data in history

Two tracked files contain what appears to be respondent-level data with
identifier columns:

```
data/CRE46-1480.dat                                        (165 KB, 1480 rows × ~50 cols)
r_reference/mokken_3.1.2/mokken/data/CRE46-1480.dat        (identical content; md5 da082bcc...)
```

The first column of both files contains 10-digit numbers (e.g.
`1134154744`, `1118205957`, `1103437230`). These do **not** match the
sequence-counter pattern of synthetic IDs — they look like
client/employee-record identifiers from the career-progression study
referenced in `docs/research_proposal.docx` (which describes a ~1,700
employee dataset; this file's 1480 rows are likely a subset).

Both copies have been in the repository since the very first tracked
commit (`0a1f314 initial state before Codex migration`).

**Risk if the repository is made public**:

- If the 10-digit IDs are real employee/client numbers from the
  partner-organisation dataset, this is a privacy incident.
- Even if the IDs are pseudonyms generated by the data provider, the
  presence of binary item responses across all 50 columns plus a stable
  identifier could allow re-identification when combined with
  organisation-level metadata.
- The fact that the file appears in `r_reference/` (where one would
  expect only the upstream R package code) suggests it was placed
  there to satisfy a relative-path expectation in an analysis script.
  Either way, **it is research data, not a published benchmark
  dataset**, and does not belong in a public open-source repo.

### Required user decisions before going public

The author (Diederick Stoel) must choose one of the following before
flipping the repository to public:

1. **Remove from history.** Run:
   ```
   git filter-repo --path data/CRE46-1480.dat \
                   --path r_reference/mokken_3.1.2/mokken/data/CRE46-1480.dat \
                   --invert-paths
   ```
   Then `git push --force-with-lease origin main` and move the file
   to the gitignored `resources/` folder for local use. **Recommended**
   if the data is genuinely identifying.

2. **Pseudonymise in place.** Replace the first column with sequential
   row numbers (`1..1480`) and rewrite history via `git filter-repo
   --replace-text rules.txt`. Acceptable if the original IDs were the
   only sensitive component.

3. **Confirm the IDs are non-identifying** and proceed. Acceptable only
   if the data provider has explicitly cleared the file for public
   redistribution, in which case attach the consent/licence
   documentation to the repo and mention it in the CHANGELOG.

4. **Keep the repository private.** Acceptable; the JOSS submission
   simply waits or moves to a derived repository without the data.

## Recommendation

**Do not make the repository public yet.** Resolve the
`CRE46-1480.dat` question first (most likely route: option 1 above —
filter-repo, since the file isn't needed for any of the
public-facing tests; only the MSP 5 `TEST.DAT` is used in
`docs/parity_results.md`). Re-run this audit script after the data is
out of history.

The JOSS submission can then proceed: tag `v0.1.0`, enable Zenodo
integration, push the tag, submit via `joss.theoj.org`.
